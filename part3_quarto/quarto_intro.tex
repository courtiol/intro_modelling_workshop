\section{What is reproducibility?}\label{what-is-reproducibility}

\begin{frame}{Reproducibility is not binary}
\protect\phantomsection\label{reproducibility-is-not-binary}
Reproducibility is best seen as a continuum within a multidimensional
space:

\begin{itemize}
\tightlist
\item
  \textbf{repeatability}: can others obtain the same results given
  access to the same data?
\item
  \textbf{transparency}: are explanations good enough to be understood
  by others?
\item
  \textbf{accessibility}: can others find and download the exact data
  and code used?
\item
  \textbf{compatibility}: can they run the code on a different
  computer/OS today?
\item
  \textbf{sustainability}: will the code still run in X years after
  package updates?
\item
  \textbf{generalisability}: can the code be applied to a new, similar
  dataset?
\end{itemize}

\pause

\vspace{1cm}

\textbf{NB:}

\begin{itemize}
\tightlist
\item
  names are my own (many synonyms exist)
\item
  improving any dimension takes intentional time/effort and introduces
  trade-offs (e.g.~improving generalisability decreases clarity)
\item
  in this very short introduction, I focus on \textbf{repeatability}
\end{itemize}
\end{frame}

\section{Why make workflows
reproducible?}\label{why-make-workflows-reproducible}

\begin{frame}{Increasing reproducibility benefits people}
\protect\phantomsection\label{increasing-reproducibility-benefits-people}
Given that reproducibility comes at a cost, the main question to answer
is:

\begin{block}{who shall benefit from the effort of making your code
reproducible?}
\protect\phantomsection\label{who-shall-benefit-from-the-effort-of-making-your-code-reproducible}
\pause

\begin{itemize}
\item
  yourself

  \begin{itemize}
  \tightlist
  \item[$\boxtimes$]
    yourself right now
  \item[$\square$]
    yourself in the near future (e.g.~writing the paper)
  \item[$\square$]
    yourself in the distant future (e.g.~analysing similar data)
  \end{itemize}
\end{itemize}

\pause

\vspace{0.5em}

\begin{itemize}
\item
  your immediate circle

  \begin{itemize}
  \tightlist
  \item[$\square$]
    your supervisor / PI
  \item[$\square$]
    your colleagues and collaborators
  \item[$\square$]
    potential reviewers, auditors, or evaluators
  \end{itemize}
\end{itemize}

\pause

\vspace{0.5em}

\begin{itemize}
\item
  the wider community

  \begin{itemize}
  \tightlist
  \item[$\square$]
    those interested in your data
  \item[$\square$]
    those interested in your research question
  \item[$\square$]
    those interested in your methodology
  \end{itemize}
\end{itemize}

\pause

\textbf{NB:} many answers can simultaneously apply
\end{block}
\end{frame}

\begin{frame}{Universal benefits of repeatable code}
\protect\phantomsection\label{universal-benefits-of-repeatable-code}
In comparison to just producing results on the fly (i.e.~taken from the
R console), writing repeatable scripts/documents provides the following
benefits:

\begin{itemize}
\tightlist
\item
  it prevents coding mistakes
\item
  exactly what you did is
  tracked\footnote<\value{beamerpauses}->[frame]{repeatable code tracks
    what code does but not how the code changed over time;\\
    the latter can instead be done using a version control system, such
    as git/GitHub}
\item
  updating the results after updating the data is easy
\end{itemize}
\end{frame}

\section{How to make workflows
repeatable?}\label{how-to-make-workflows-repeatable}

\begin{frame}{Various approaches can be used to improve repeatability of
R-based workflows}
\protect\phantomsection\label{various-approaches-can-be-used-to-improve-repeatability-of-r-based-workflows}
\footnotesize

\begingroup\fontsize{10}{12}\selectfont

\begin{longtable*}[t]{lccc}
\toprule
Tool & Literate programming** & Setup & Learning curve\\
\midrule
R script & no & simple & low\\
R package* & yes & difficult & high\\
sweave & yes & medium & high\\
rmarkdown/quarto & yes & simple & low/mid\\
\bottomrule
\end{longtable*}
\endgroup{}

\normalsize

*i.e a specific R package which main goal is to reproduce the results of
a workflow

**mixing prose and code

\pause

\textbf{Conclusion:}

\begin{itemize}
\tightlist
\item
  rmarkdown/quarto improves repeatability at low cost
\item
  syntax errors in rmarkdown/quarto can be frustrating, but LLMs are
  exceptionally efficient at debugging these specific issues
\item
  quarto can do the same \& more than rmarkdown, so I will focus on that
\end{itemize}
\end{frame}

\begin{frame}{The header}
\protect\phantomsection\label{the-header-2}
The header is a particularly fragile component

\begin{itemize}
\tightlist
\item
  spacing matters
\item

\begin{frame}[fragile]{The body of text}
\protect\phantomsection\label{the-body-of-text}
This is the easy part

\begin{itemize}
\tightlist
\item
  write plain text and use \texttt{\#}, \texttt{\#\#}, \texttt{\#\#\#}
  to define a hierarchy of sections\\
  (if the hierarchy is messed up it can be because a chunk is located at
  the highest level of the hierarchy)
\item
  use \texttt{*text*}, \texttt{**text**}, \texttt{***text***}, to create
  \emph{text}, \textbf{text} \& \textbf{\emph{text}}, respectively
\item
  use \texttt{{[}link\_text{]}(weblink)} to create hyperlinks
\item
  use
  \texttt{!{[}Figure\ legend{]}(path\_to\_figure/fig.png)\{height=Xcm\}}
  to add a figure of Xcm in height*
\end{itemize}

\vfill

\pause

*\footnotesize to add figures, you can alternatively use HTML, LaTeX, or
R commands. I prefer using the R command provided by \{knitr\} since it
works well irrespective of the output format: inside a chunk of R code
(see next slide), use
\texttt{knitr::include\_graphics("path\_to\_figure/fig.png")}; you can
influence the formatting via chunk options
(e.g.~\texttt{\#\textbar{}\ out-height:\ Xcm},
\texttt{\#\textbar{}\ fig-align:\ center})

\section{Beyond repeatability}\label{beyond-repeatability}

\begin{frame}[fragile]{How to improve other aspects of reproducibility}
\protect\phantomsection\label{how-to-improve-other-aspects-of-reproducibility}
\begin{itemize}[<+->]
\tightlist
\item
  \textbf{transparency}: document \emph{why} you do things and not just
  \emph{how} you do things
\item
  \textbf{accessibility}: host your data and code on platforms such as
  GitHub, Zenodo, \ldots{}
\item
  \textbf{compatibility}: make sure to try your code on other computers
\item
  \textbf{sustainability}: minimize external dependencies; at a minimum
  document package versions using \texttt{sessionInfo()}, or better use
  systems such as \{renv\} which save and load specific versions of R
  packages; for longer sustainability learn how to build containers
  (e.g.~docker)
\item
  \textbf{generalisability}: design functions, do not hardcode
  parameters, do not use indices
\end{itemize}

\pause

\vspace{1cm}

\textbf{NB:}

\begin{itemize}
\tightlist
\item
  many of these improvements can be achieved at minimal costs
\item
  remember that repeatability is a continuum (e.g.~the more
  generalizable the code one wants, the more effort one must put into
  creating the code)
\end{itemize}
\end{frame}
